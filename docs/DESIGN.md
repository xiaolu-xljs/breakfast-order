# 早餐店扫码点餐系统 — 设计方案

> 面向单店堂食场景，顾客扫码 → 看菜单 → 下单 → 微信支付 → 等餐；商家在后台管理菜单、接收订单。

---

## 1. 系统全景

整个产品由 3 个端组成：

```
┌─────────────────┐      ┌──────────────────┐      ┌─────────────────┐
│  顾客端         │      │  后端 API 服务   │      │  商家管理后台    │
│  (微信小程序)    │ ←→  │  (Node.js)      │ ←→  │  (Web 浏览器)   │
└─────────────────┘      └──────────────────┘      └─────────────────┘
        │                         │                         │
        ↓                         ↓                         ↓
   微信支付                数据库 (MySQL/SQLite)        二维码生成
   订阅消息推送            Redis (缓存/队列)            数据统计
```

| 端 | 用户 | 形态 | 主要职责 |
|---|---|---|---|
| 顾客端 | 进店顾客 | 微信小程序 | 扫码、看菜单、下单、付款、查订单 |
| 后端 API | 系统内部 | Node.js 服务 | 提供所有业务接口、对接微信支付 |
| 商家后台 | 店主/店员 | Web 页面（电脑/手机浏览器打开） | 菜单管理、订单接收、餐桌管理、统计 |

## 2. 用户流程

### 2.1 顾客点餐流程（最常见路径）

```
[坐下] → 扫桌上二维码 → 进入小程序（自动带入桌号）
       → 看菜单 → 加入购物车 → 提交订单
       → 微信支付 → 看到「已下单，等餐中」
       → 收到「您的餐已出，请到 XX 桌取餐」推送
```

### 2.2 商家接单流程

```
[有新订单] → 后台弹窗 + 声音提醒
           → 看到桌号 + 菜品明细
           → 点击「制作中」→ 点击「已出餐」
           → （顾客端状态自动更新 + 微信推送）
```

### 3.1 顾客端（小程序）

| 模块 | 功能 | 优先级 |
|---|---|---|
| 扫码进入 | 识别餐桌二维码、自动带入桌号 | P0 |
| 菜单浏览 | 按分类展示商品（图片/名称/价格/简介） | P0 |

## 4. 数据模型（数据库表设计）

下面这些是核心表，每张表的关键字段列出。

### 4.1 商品分类 `categories`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | int | 主键 |
| name | string | 分类名（如「包子类」「饮品类」） |
| sort_order | int | 显示顺序 |
| is_active | bool | 是否启用 |

### 4.2 商品 `products`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | int | 主键 |
| category_id | int | 所属分类 |
| name | string | 商品名 |
| price | decimal | 单价（元） |
| description | string | 简介（可选） |
| image_url | string | 商品图（可选） |
| is_available | bool | 是否可售（临时下架用） |
| sort_order | int | 排序 |

### 4.3 餐桌 `tables`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | int | 主键 |
| table_no | string | 桌号（如「A01」「B12」） |
| qr_code_url | string | 二维码图片地址 |
| is_active | bool | 是否启用 |

### 4.4 订单 `orders`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | int | 主键 |
| order_no | string | 订单号（顾客可见，如 YYYYMMDDHHMMSS+随机） |
| table_id | int | 餐桌 |
| total_amount | decimal | 总金额 |
| status | enum | 状态：`paid`(已付款待处理) / `preparing`(制作中) / `served`(已出餐) / `completed`(已完成) / `cancelled`(已取消) |
| paid_at | datetime | 支付时间 |
| created_at | datetime | 下单时间 |
| openid | string | 顾客微信 openid（用于推送） |

### 4.5 订单项 `order_items`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | int | 主键 |
| order_id | int | 所属订单 |
| product_id | int | 商品 |
| product_name | string | 商品名（冗余，防止商品改名后历史订单看不清） |
| price | decimal | 下单时单价 |
| quantity | int | 数量 |
| subtotal | decimal | 小计 |

### 4.6 管理员 `admins`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | int | 主键 |
| username | string | 账号 |
| password_hash | string | 加密后的密码 |
| name | string | 显示名 |

## 5. 接口设计（API 概览）

按 REST 风格，分 4 个组。

### 5.1 顾客端（无需登录，但记录 openid）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/menu` | 获取菜单（分类 + 商品） |
| POST | `/api/orders` | 创建订单（桌号 + 商品列表） |
| GET | `/api/orders/:id` | 查询订单状态 |
| POST | `/api/pay/wxpay` | 调起微信支付（返回支付参数） |
| POST | `/api/pay/notify` | 微信支付回调（后端内部用） |

### 5.2 商家端（需要登录）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/admin/login` | 登录 |
| GET | `/api/admin/orders` | 订单列表（支持按状态/日期筛选） |
| PATCH | `/api/admin/orders/:id/status` | 改订单状态 |
| CRUD | `/api/admin/categories` | 分类管理 |
| CRUD | `/api/admin/products` | 商品管理（含图片上传） |
| CRUD | `/api/admin/tables` | 餐桌管理 |
| GET | `/api/admin/tables/:id/qrcode` | 生成/获取该桌二维码 |
| GET | `/api/admin/stats/overview` | 营业数据概览 |

## 6. 技术选型

针对你**没有技术背景**，我选择「最容易上手、最容易部署、对微信生态最友好」的组合。

### 6.1 顾客端：微信小程序（原生）

- **为什么**：唯一能直接对接微信扫码、微信支付、订阅消息的形态；体验最佳。
- **要求**：需要你注册一个**微信小程序账号**（个人主体可免费注册，但收款受限；建议用个体工商户或企业主体，后续申请微信支付商户号）。

### 6.2 后端：Node.js + Express + Prisma

- **为什么**：JS 生态丰富、文档多、后期维护成本低、腾讯云开发对 Node.js 支持好。

### 6.3 数据库：开发期 SQLite → 上线期 MySQL

- **为什么**：开发期零配置；上线期切到 MySQL 即可（Prisma 切换很简单）。

### 6.4 商家后台：Vue 3 + Element Plus（Vite 构建）

- **为什么**：组件库成熟、文档好；既能在电脑上用，手机浏览器也能打开。

### 6.5 部署（上线时考虑）

- **推荐**：微信云开发 / 腾讯云开发 — 无需自己买服务器，一键部署，自动 HTTPS，跟小程序无缝打通。
- 备选：阿里云、腾讯云 CVM（自己装环境，门槛更高）。

### 6.6 图片存储

- 商家后台上传的商品图，存到云存储（如腾讯云 COS），不放在数据库里。

## 7. 二维码方案

- 每张餐桌在后台录入，生成一个唯一短链接：`https://你的域名/m?table=A01`
- 把这个链接生成二维码，打印贴在桌上
- 顾客扫码 → 小程序解析 URL 中的 `table=A01` → 自动带入桌号

> 上线前也可以生成一个**通用二维码**（不带桌号），顾客点餐时自己选桌号，先把流程跑通。

## 8. 微信支付流程

```
[顾客提交订单] → 后端生成订单号、调用「微信支付统一下单 API」
              → 返回支付参数给小程序的 wx.requestPayment
              → 顾客输入密码完成支付
              → 微信服务器回调后端的 /api/pay/notify
              → 后端更新订单状态为「已付款」
              → 后端触发「订阅消息」通知到顾客（可选）
              → 后台弹窗「新订单」，商家开始处理
```

> **前提条件**：需要一个**微信支付商户号**。个体工商户可申请，资料齐全 1-3 个工作日下号。

## 10. 开发节奏（分阶段实现）

按从核心到外围的顺序，每一阶段都能独立跑通、看到效果。

| 阶段 | 内容 | 验收标志 |
|---|---|---|
| **阶段 1** | 后端骨架 + 数据库 + 菜单 API | 能在命令行/Postman 拿到菜单数据 |
| **阶段 2** | 商家后台（菜单 CRUD + 分类 + 商品） | 后台能加分类、加商品、看商品列表 |
| **阶段 3** | 顾客小程序（菜单浏览 + 购物车 + 下单） | 小程序能下单（先不接支付） |
| **阶段 4** | 商家后台（订单接收 + 状态切换） | 后台能看新订单 + 改状态 |
| **阶段 5** | 微信支付对接（需要商户号） | 真支付能跑通 |
| **阶段 6** | 餐桌管理 + 二维码生成 | 能生成每张桌的二维码 |
| **阶段 7** | 订阅消息 + 营业统计 | 顾客能收到状态推送，后台有统计 |
| **阶段 8** | 部署到云开发 + 上线 | 正式可用 |

## 11. 风险与前置准备（你需要知道）

### 11.1 必须你本人准备的资质

1. **微信小程序账号**
   - 个人可注册，但功能受限（无微信支付）
   - 建议：个体工商户 / 企业主体注册，公众号「微信公众平台」申请

2. **微信支付商户号**
   - 需要营业执照、法人身份证、对公账户（个体户可用法人个人银行卡）
   - 申请地址：pay.weixin.qq.com
   - 资料齐全下号周期：1-3 个工作日

3. **服务器域名 + SSL 证书**
   - 微信要求所有 API 必须是 HTTPS
   - 用云开发可以省掉这步

### 11.2 不属于本期的内容

- ❌ 外卖配送
- ❌ 多商家入驻（多租户）
- ❌ 后厨打印机对接
- ❌ 营销活动（优惠券、满减、积分）
- ❌ 数据导出（Excel 报表）
- ❌ 退款流程

这些都可以后续加，先把核心下单跑通。
